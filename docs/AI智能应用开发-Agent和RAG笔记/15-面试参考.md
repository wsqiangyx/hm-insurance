# 1. 项目介绍：先讲清商城，再讲智能客服

## 1.1 项目背景与业务定位
安心保是一个面向个人和家庭用户的在线保险商城，聚合医疗险、重疾险、寿险、意外险等产品，围绕保险选购、方案配置、投保办理、保单管理和售后咨询提供一站式服务。用户既可以在商城页面中自主操作，也可以通过智能保险顾问，以自然语言完成咨询和业务引导。
项目不是单纯在页面中接入一个聊天窗口，而是把智能客服与商城的产品、方案、保单、理赔等业务能力连接起来：回答产品问题时查询真实产品数据，解释保障责任时检索对应条款，生成方案后交给用户确认，涉及业务办理时调用明确的业务接口。
保险选购的核心难点在于信息复杂和决策链长。用户通常知道自己的年龄、预算和家庭情况，却不清楚应该选择哪些险种，也难以独立理解等待期、免赔额、责任免除等条款。售后阶段，用户又需要理解理赔材料、办理流程和进度。智能顾问的价值就是把这些分散信息转化为可理解、可操作的服务。

## 1.2 商城包含哪些业务模块

| 业务模块 | 用户可以做什么 | 与智能客服的关系 |
| --- | --- | --- |
| **产品中心** | 按险种浏览产品，查看产品介绍、保障亮点和主条款 | 为产品咨询、候选筛选和方案推荐提供结构化数据 |
| **保费测算** | 按照产品定价模板填写年龄、保障计划等条件，取得测算结果 | 顾问引导补齐条件；具体金额由业务计算能力返回 |
| **保险方案** | 查看组合方案、产品明细、预算分配和推荐理由，跟踪投保状态 | 顾问生成方案，通过确认交互保存并展示产品卡片 |
| **投保与订单** | 从方案或产品进入投保流程，关联报价、订单及后续状态 | 顾问帮助理解流程，关键业务动作交给确定性接口 |
| **保单管理** | 查看已持有保单、保障期限、被保人和保单状态 | 为已购保障咨询和理赔咨询提供业务上下文 |
| **理赔服务** | 查看理赔记录与进度，获取申请表、材料清单和办理指引 | 根据保单定位产品，结合条款和业务记录解释 |
| **智能客服与会话** | 多轮咨询，切换或重命名会话，查询历史，查看引用，处理确认 | 统一承载不同工作流，保持上下文和可恢复的交互状态 |
理赔服务的定位是信息查询和办理指引，实际受理、审核和赔付由承保机构完成。介绍项目时应把商城服务与保险公司的业务职责说清楚，这也是理解业务边界的一部分。

## 1.3 用一条用户旅程串起全貌
第一步，用户进入商城，按分类查看产品。如果不知道如何选，可以向顾问说：“我今年32岁，是程序员，预算2万元以内，希望先把基础保障配齐。”
第二步，顾问通过多轮对话了解用户需求，调用候选产品工具取得真实产品，再形成组合建议。用户追问“这款医疗险的免赔额怎么计算”，顾问针对该产品检索条款，给出带引用的解释。
第三步，用户认可组合后，系统展示方案确认卡片。确认保存后，方案进入业务数据库，用户可以在页面中继续查看产品、进行保费测算、进入投保流程。推荐预算只是配置建议，实际测算金额以业务接口结果为依据。
第四步，用户在保单中心查看保障情况。后续遇到理赔问题，可以在同一个客服入口询问材料要求或进度，系统切换到理赔工作流，结合保单、理赔记录和条款提供回答。
这条链路体现了项目的两条主线：商城承载确定性的业务操作；智能顾问负责理解需求、组织信息、调用能力并引导用户完成下一步。

## 1.4 智能客服为什么划分多个工作流
同样是“问保险”，实际任务可能完全不同。购买前关注产品和预算，购买后关注保单和理赔；闲聊不需要访问业务数据库，保存方案却会改变业务数据。如果把所有规则和工具放入一个大 Prompt，模型需要同时判断过多事情，业务边界也不清晰。

| 工作流 | 典型输入 | 主要职责 |
| --- | --- | --- |
| **闲聊** | 你好；聊点别的 | 处理寒暄和有限闲聊，自然引导回保险业务 |
| **保险方案咨询与推荐** | 我该买什么；这款免责范围是什么 | 产品咨询、条款问答、组合建议、方案确认与保存、投保引导 |
| **理赔咨询** | 这张保单怎么申请理赔；进度到哪了 | 定位保单，查询记录，解释材料和条款 |
| **转人工** | 我要联系人工；问题需要人工处理 | 承接明确的人工服务需求 |
| **兜底** | 无法可靠判断的输入 | 说明可提供的服务，澄清用户需求 |
这里不是“每个接口对应一个 Agent”。产品咨询、条款问答和方案推荐可以由同一个保险顾问完成；划分依据是任务目标、上下文和工具边界，而不是功能名称的数量。

## 1.6 三分钟项目介绍：展开重点与口述示例
先讲业务闭环：这是保险商城，服务包含选购、咨询、方案、投保、保单和售后；AI 是统一的自然语言服务入口，而不是替代整个交易系统。
再讲两个技术难点。第一个是条款问答：保险条款结构复杂，产品之间内容相似，直接检索容易出现命中错误产品或上下文不完整。我们从解析、结构修复、父子块、产品过滤、混合召回和重排几个环节处理，最后把依据展示给用户。
第二个是 Agent 可控性：不同用户需求要进入不同工作流；保存方案不能仅凭模型决定；刷新页面后也要继续看到会话和待确认内容。因此采用主图编排、子 Agent 处理业务、Context 传递用户身份、Checkpointer 持久化状态、interrupt 暂停恢复。
最后用一个例子收尾：用户提出预算和年龄，顾问查候选产品；追问免责条款时调用 RAG；确认组合后展示确认卡片并保存。这展示的是模型理解、知识检索和确定性业务操作之间的协作。
**完整口述示例（约三分钟，可根据个人语速适当精简）：**
> 我参与的项目叫安心保，是一个面向个人和家庭用户的在线保险商城，聚合了医疗险、重疾险、寿险和意外险等产品。业务上覆盖产品浏览、保费测算、保险方案、投保与保单管理，以及理赔查询和办理指引。我们在商城中接入智能保险顾问，希望用户不仅能自己浏览产品，也能通过对话获得选购建议和售后帮助。
> 这个项目要解决的主要问题是，保险产品多、条款专业，用户虽然知道自己的预算和需求，却不一定知道怎么搭配产品，也很难从几十页条款里找到准确依据。所以智能顾问不能只是聊天，还需要查询商城数据、检索条款，并连接后续的业务操作。
> 我主要负责智能顾问后端的 Agent、RAG 和流式对话部分。产品、投保、保单和理赔等业务模块由其他后端同事负责，我负责与他们约定工具需要的参数和返回结果。整体采用前后端分离架构，后端是 FastAPI 模块化单体，业务数据使用 PostgreSQL，条款检索使用 Milvus。
> RAG 这部分，我先用 MinerU 把条款 PDF 解析成 Markdown，再通过模型整理不规则的标题和表格结构。切分时采用父子块：完整章节作为父块存入 PostgreSQL，再切成较小的子块写入 Milvus。查询时结合稠密向量和 BM25 召回，通过重排选出相关子块，再回查完整父块交给模型。这样既能定位具体问题，又能保留条款中的条件和例外。同时按 product_id 限定检索范围，避免把不同产品的条款混在一起，回答也能点击引用查看原文。
> Agent 这部分，我使用 LangGraph 主图做意图识别和工作流分发，区分闲聊、保险咨询推荐、理赔等任务。保险顾问子 Agent 用 LangChain 创建，按需调用候选产品查询、条款检索和方案保存工具。用户身份由服务端通过 Context 传入，不让模型自己填写；方案保存前通过 interrupt 暂停，展示确认卡片，用户批准后再恢复执行并写入数据库。
> 在工程接入上，我通过 FastAPI 的生命周期管理主 Graph 和连接池，使用 PostgreSQL Checkpointer 保存会话状态，再通过 SSE 把回复片段、引用来源和确认信息传给前端。引用信息会与对应的 AI 消息关联保存，因此刷新页面后，历史回答和引用仍然能够一起展示。
> 举个例子，用户说自己32岁、预算两万元，顾问会先补齐需求、查询候选产品并给出组合建议；用户追问某款产品的免赔额时，会检索对应条款并附上依据；认可方案后再确认保存。我这部分工作的重点，就是把模型理解、知识检索和业务操作连接成一条可控、可追溯的服务链路。

## 1.7 团队分工与个人职责表达
团队分工示例：商城业务同事负责产品、定价、投保、订单、保单和理赔接口；前端同事负责商城页面及客服交互；我负责智能顾问的工作流、工具集成、条款知识库和对话接口，并与业务同事约定工具所需字段、状态和错误语义。
面试中先说明团队交付了什么，再说明自己负责什么。讲到保费、保单或理赔时，可以说明“这个模块由业务同事负责，我负责将其查询或办理能力接入客服工作流”，随后展开接口契约、用户归属校验和工具调用，而不必把每个模块都说成自己独立实现。

# 2. 项目架构与核心链路

## 2.1 整体架构：前后端分离，后端模块化
项目采用前后端分离架构，frontend 使用 React 和 Ant Design，agent-service 使用 FastAPI。agent-service 是模块化单体：传统业务与 AI 能力按包划分职责，在同一个后端应用内协作。业务分层不等于拆成多个微服务，调用 Service 也不意味着发起远程请求。
前端有两个主要入口：商城页面通过普通 HTTP 接口操作产品、方案和保单；客服窗口通过统一对话接口进入主 Graph，接收 SSE 文本、引用和确认事件。两条入口复用业务能力，避免各自实现一套规则。

| 层次 | 项目位置或组件 | 职责 |
| --- | --- | --- |
| HTTP 接入 | app.modules.*.router | 请求校验、依赖注入、普通响应或 SSE 输出 |
| 业务逻辑 | app.modules.*.service | 用户归属、业务编排、事务与规则 |
| 数据访问 | app.modules.*.repository | 执行查询和持久化，不决定推荐策略 |
| 智能体 | app.agents | 主 Graph、意图路由、子 Agent、工具及状态定义 |
| 知识检索 | app.rag | Pipeline、父块 Model/Repository、自定义异步 Retriever |
| 基础设施 | app.infra | 业务数据库、Checkpointer 及连接资源 |
| 公共配置 | app.core | 模型、数据库和 RAG 等配置 |

## 2.2 关键技术各自解决什么问题

| 技术 | 在本项目中的用途 |
| --- | --- |
| LangChain | 统一模型和工具调用；使用 create_agent 构建保险顾问 |
| LangGraph | 主图路由、子图编排、State、检查点和中断恢复 |
| PostgreSQL + SQLAlchemy | 产品、方案、会话元数据、父块等结构化数据 |
| PostgreSQL Checkpointer | 会话执行状态与消息的持久化，支持恢复和历史查询 |
| Milvus + langchain-milvus | 子块稠密/BM25 检索、产品过滤、重排接入 |
| MinerU | 解析条款 PDF，输出可进一步处理的 Markdown |
| Ollama Embeddings | 生成文档与查询的稠密向量 |
| Reranker | 对候选问题—文本对重新评估相关性 |
| FastAPI SSE | 持续推送回复片段、附加信息与确认内容 |
| Docker Compose | 组织数据库、Milvus 及配套依赖的运行环境 |
选择这些组件是因为它们能组成同一条可落地的链路，不是因为技术名词越多越好。例如不单独再写 Embedding 或 VectorStore 抽象层，而是复用现有组件，把项目代码集中在条款处理和父块回查这些业务差异上。

### 2.4.1 RAG 离线阶段
离线流程Pipeline：

> [画板内容，请在原文查看]
产品主条款 PDF → MinerU 解析 → Markdown 结构优化 → 按章节生成父块 → 在父块内递归切分子块 → 父块写 PostgreSQL → 子块写 Milvus，生成稠密和 BM25 稀疏表示。

### 2.4.2 RAG 在线阶段
流程图：

> [画板内容，请在原文查看]
用户问题 → Agent 确认目标产品 → 条款检索工具 → Retriever 按 product_id 过滤 → 稠密与 BM25 多路召回 → 重排选出子块 → parent_id 有序去重 → PostgreSQL 批量回查父块 → 基于完整条款回答。
“命中子块，返回父块”是关键：子块让检索聚焦问题，父块为生成提供更完整的责任、条件和例外。SQL 的 IN 查询不保证结果顺序，所以回查后按照已排序的 parent_id 列表重建返回顺序。
来源信息分成两条输出：一份随工具结果交给模型，用于正文引用；一份通过 custom 事件转成 additional_info 发给前端，用于展示条款文件名、章节和原文。会话结束时，再把附加信息关联到对应 AI 消息并持久化。

## 2.5 业务事实、知识依据和会话状态为什么分开存

| 数据 | 主要存储 | 为什么 |
| --- | --- | --- |
| 产品、方案、保单、理赔状态 | PostgreSQL 业务表 | 需要准确查询、归属校验和事务，不适合靠语义相似度决定 |
| 完整条款父块 | PostgreSQL parent_chunks | 根据 ID 获取原文和溯源元数据 |
| 子块及稠密/稀疏向量 | Milvus | 用于相关性检索和产品范围过滤 |
| 消息与 Graph 执行状态 | Checkpointer | 保存工作流上下文和可恢复状态 |
| 当前调用的用户身份 | Runtime Context | 由服务端传入，不能让模型自行填写 |
一个容易混淆的点是：向量库不是业务数据库，Checkpointer 也不是业务数据库。查询理赔进度应查业务记录，解释免责条款应查知识库，延续上次对话应读会话状态。

## 2.6 一次流式对话的完整执行过程
前端提交 thread_id 和 message；ChatService 先确认会话属于当前用户，再向主 Graph 传入本轮 HumanMessage、thread_id 和运行时 Context。
Graph 从检查点恢复该会话的状态，路由到具体工作流。子 Agent 调用模型和工具，ChatService 遍历 v3 事件流，识别可展示的文本增量与 custom 附加信息，再转换成前端约定的 message、additional_info 等 SSE 事件。
如果工具触发 interrupt，前端展示确认卡片；用户提交 decision 后，服务端在同一个 thread_id 上使用 Command(resume=...) 恢复。正常流结束前完成必要的引用状态关联，最后发送 done，前端结束本轮 loading。
前端不需要理解主图、子图、工具节点等内部事件。后端事件适配层把内部执行协议转换为稳定的业务展示协议。

## 2.7 生命周期与并发隔离
在 FastAPI lifespan 中初始化 Checkpointer 连接池和主 Graph，将可运行 Graph 保存在 app.state.agent，通过构造函数注入 ChatService。应用关闭时释放连接池等资源。
共享的是可复用的 Graph、模型客户端和连接池，不是用户的对话状态。用户身份通过每次调用的 Context 传递，会话通过 thread_id 区分；工具需要数据库时创建独立 Session，不能把某个用户的 Session 或 user_id 放入共享全局变量。
RAG 的共享 Embedding、VectorStore 和 Retriever 在 app.rag 包统一组织。Retriever 本身不保存某个用户的问题，product_id 等查询条件随每次调用传入，因此不需要为了传递它而层层放入对话 State。

# 4. RAG 专题面试题与参考答案
> **答题建议：**这一组题建议按"业务问题 → 处理链路 → 设计取舍 → 验证方法"回答。不要只解释框架概念，要始终回到保险条款为什么需要这样处理。

## 4.1 为什么保险条款问答选择 RAG，而不是直接问大模型？
> **可能追问：**为什么不微调？微调更适合调整行为和任务表现，不能替代产品条款的按需读取、更新和引用。这个项目的关键需求是依据可更新、来源可查看，因此优先解决检索链路。
> **参考回答：**保险条款是产品级知识，既包含专业表达，也包含版本、责任范围和限制条件。通用模型即使知道什么是免赔额，也不能据此判断某一款产品的具体约定。我们的目标不是让模型背出保险常识，而是让它依据用户正在咨询的产品条款回答。
> 因此把条款建成知识库，在回答前取得相关原文。产品价格、保单状态等结构化事实仍然从业务接口查询。RAG 提供知识依据，业务工具提供实时业务事实，模型负责理解和表达。相比把所有 PDF 都塞进上下文，按需检索也能减少无关信息。

## 4.2 请完整介绍一次条款问答的数据流。
> **可能追问：**这里至少能分出五个可检查的结果：查询条件、召回子块、重排结果、回查父块、最终答案与引用。任何一步错误都可以沿这条链定位，不必把问题全部归结为模型。
> **参考回答：**假设用户已经在咨询 product_id=6，并追问免赔额如何计算。保险顾问先把上下文中的产品身份与本轮问题结合，调用条款工具，传入 product_id 和 query。Retriever 在该产品范围内进行稠密与 BM25 召回，用重排模型选出相关子块。
> 随后提取 parent_id，按首次出现顺序去重，批量查询 PostgreSQL 中的父块并恢复相关性顺序。工具把完整条款和来源标识交给模型，同时发出自定义来源事件。模型基于这些依据组织解释，前端根据引用标识展示对应文件名、章节和原文。

## 4.3 为什么用 MinerU 解析 PDF，解析完为什么还要优化 Markdown？
> **参考回答：**条款 PDF 不是简单连续文本，可能有跨页表格、合并单元格、多栏以及嵌在表格中的章节标题。纯文本抽取容易失去阅读顺序和层级，所以我们使用 MinerU 做版面和内容解析，先转成 Markdown。
> 但“能提取文字”不等于“结构适合切分”。例如标题仍然在表格中、同一章节被跨页拆散，后续按标题切分就无法得到正确父块。我们比较过人工整理、规则替换和模型处理，规则处理固定噪声比较合适，面对不同产品的不规则结构则采用模型辅助调整层级。约束是修复结构，不改写责任、金额、时间和否定词。
> **可能追问：**怎么判断优化正确？
> 重点比对原文关键事实、表格行列关系、标题归属和正文覆盖，不以语言更通顺作为标准。解析错误不会因为下游增加重排就自动消失。

## 4.4 为什么不直接固定长度切分，而要父子块？
> **可能追问：**父块是不是越大越好？不是。父块过大会增加上下文成本和噪声，所以章节结构要合理；不应把整份几十页条款作为一个父块，再声称采用了父子块就解决问题。
> **参考回答：**用户问的是一个具体点，例如免赔额能否累计抵扣；但完整解释可能还依赖同一条款中的适用范围和例外。如果块过小，容易只拿到半句话；如果块很大，不同主题被一个向量混合表达，命中又不够聚焦。
> 我们让父块按章节承载完整语境，再在父块内部递归切分子块。子块用于相关性匹配，命中后回查父块给模型。它不是保证任何问题都能正确回答的魔法，而是把检索粒度与生成上下文粒度拆开，针对条款的结构特点取得平衡。

## 4.5 父块、子块具体存哪些字段？为什么手动生成父块 ID？
> **参考回答：**父块保存 id、product_id、clause_name、section_path、content。id 是父块的稳定关联键，product_id 确定产品范围，clause_name 和 section_path 用于来源展示，content 是回传给模型的正文。子块保留检索文本、product_id、parent_id，以及稠密和稀疏检索字段。
> 父块 ID 在切分阶段就生成，子块当场记录 parent_id。这样处理结果在内存中已经形成完整关系，不需要先把父块插入数据库、再拿自增 ID 回填子块。子块自身可以由向量库生成主键，两种 ID 的用途不同。
> **可能追问：**clause_name 为什么放在父块？在线最终返回的是父块，从父块就能拿到完整溯源信息，避免为每个引用再查产品表。当前用文件名展示，不意味着文件名就是父块唯一标识。

## 4.6 为什么给子块添加 section_path？它和 product_id 有什么区别？
> **可能追问：**标题越多越好吗？不是。只补充该子块所属的路径，避免将整篇目录重复拼进去；否则重复标题会增加噪声，也可能影响关键词得分。
> **参考回答：**很多条款片段单独看只有“发生下列情形”“上述费用”等表述。把章节路径加入子块检索文本，可以让 Embedding 和关键词检索看到它属于哪类责任，提高片段的可理解性。
> section_path 提供语义上下文，product_id 则是明确的业务过滤条件。标题中写了产品名称并不等于完成了隔离，模型相似度也不负责保证产品身份正确。我们仍然把 product_id 当标量字段用于检索范围过滤。

## 4.7 稠密检索和 BM25 在这个项目中分别解决什么问题？
> **参考回答：**用户往往说“哪些情况不赔”，条款可能写“责任免除”。稠密向量通过语义表示处理这种不同措辞。另一方面，产品名称、条款编号和专业名词的字面差异也很重要，BM25 能利用词项匹配补充这类信号。
> 项目使用 Embedding 生成稠密向量，BM25 稀疏表示由 Milvus 的内置能力配合中文分析器处理。一段文本只涉及有限词项，因此稀疏表示只需存非零权重。这里说的是本项目的 BM25 路线，不是所有稀疏模型都只能做字面匹配。
> **可能追问：**纯向量也能准确找关键词，还要 BM25 吗？一次成功不能代表整个问题集。混合检索的价值是让两种信号互补，应比较口语问法、编号、相近产品和专业词等多类查询，而不是刻意找一条纯向量必败的例子。

## 4.8 混合检索的结果怎么融合？RRF、加权、模型重排有什么差别？
> **可能追问：**为什么不直接让重排模型扫描全部条款？因为逐对评估有成本。先召回较小候选集，再精排，才发挥两阶段设计的价值。
> **参考回答：**稠密和 BM25 分别召回候选，分数不是天然可直接相加的同一尺度。加权融合需要适当的分数处理和权重选择；RRF 利用各路名次的倒数贡献进行融合，减少对原始分数尺度的依赖。
> 模型重排则把问题和候选文本一起交给 Reranker，重新判断它们的相关性。前两种主要组合检索信号，后一种重新阅读候选内容。课程对比了这些方案，项目的在线检索接入模型重排；不需要把 RRF、加权和模型重排全部串起来才叫混合检索。

## 4.9 Embedding 和 Reranker 的原理与职责有什么不同？
> **参考回答：**稠密检索中，文档向量可以在离线阶段预计算。查询时只计算问题向量，再做相似度搜索，所以适合从较大集合中快速找候选。它的限制是问题和文档分别编码，细粒度关系可能没有被充分体现。
> Cross-Encoder 类重排会联合处理当前问题与候选文本，能够进一步判断候选是在回答问题、只是提到同一主题，还是给出一个限制条件。但这部分计算依赖当前问题，不能像文档向量那样全部提前完成。
> **可能追问：**为什么 Rerank Function 中带 queries？因为这次重排描述的就是“当前问题与这批候选”的计算任务。模型客户端和配置可以复用，但请求级 query 应独立，避免并发请求互相覆盖；创建请求描述对象不等于每次加载模型权重。

## 4.10 top_k 和 fetch_k 怎么选？返回 5 个子块就一定有 5 个父块吗？
> **可能追问：**如何调参？固定问题集，分别观察召回覆盖、排序质量、父块重复率、回答依据充分程度和耗时，再决定参数，而不是把某个数字作为所有知识库通用的最佳值。
> **参考回答：**fetch_k 用来控制候选召回规模，k 控制最终选择规模，但不同封装对参数的具体含义需要看实际调用。项目把更多子块交给重排，再选择较少结果回查父块，以平衡覆盖率和处理成本。
> 多个高相关子块可能属于同一个父块，因此 5 个子块去重后可能只剩 2 个父块。评估时除了子块命中，还要看父块数量、章节覆盖和总上下文长度。盲目增大 k 可能只是多拿重复章节，甚至增加无关信息。

## 4.11 为什么先按 product_id 过滤，不能检索后再检查吗？
> **可能追问：**用户只说“这款”怎么办？先利用当前对话确认指代；仍然不明确就澄清，而不是随意取一个产品 ID。正确过滤建立在正确识别产品的前提下。
> **参考回答：**多款保险产品都有等待期、责任免除、免赔额等相似章节。如果先从所有产品里取全局 TopK，再剔除其他产品，TopK 名额可能已经被别的产品占满，最终目标产品没有结果。
> 所以把 product_id 放进检索条件，让候选从一开始就在目标范围中产生。它约束的是“哪些文档可以参与检索”，重排解决的是“这些候选谁更相关”，两者不能替代。多产品对比时可分别按各自 ID 检索，再明确归属地组织答案。

## 4.12 回查父块为什么要去重和重新排序？
> **参考回答：**假设重排结果的 parent_id 依次是 P3、P1、P3、P2，最终需要 P3、P1、P2。去重避免同一长章节重复进入上下文，同时保留首次命中的排序信号。
> Python 字典保留插入顺序，所以 list(dict.fromkeys(...)) 可以得到这个顺序。但数据库 WHERE id IN (...) 不保证按参数顺序返回，所以先批量查询、建立 id 到父块的映射，再按 P3、P1、P2 组装。不能把字典有序与 SQL 返回有序混为一谈。
> **可能追问：**为何不逐个查询？批量回查减少数据库往返。若某个父块不存在，应识别数据关联问题，不能把不存在的内容补造出来。

## 4.13 Agentic RAG 和固定检索链有什么区别，为什么本项目这样选？
> **可能追问：**Agentic RAG 一定更好吗？不是。它增加模型决策和可能的调用轮次。对于单纯的条款问答 API，固定链可能更直接；我们采用它是因为需要与商城其他工具协作。
> **参考回答：**固定检索链通常明确规定先检索再生成，适合请求本身就是知识问答的入口。我们的客服还要处理寒暄、查产品、生成方案和业务查询，不是每句话都需要访问条款库。
> 因此把条款检索封装为工具，由保险顾问结合任务和上下文决定何时调用、用什么问题调用。固定的部分仍然由 Retriever 完成：过滤、召回、重排和父块回查都不是让模型自由编排。也就是说，灵活性放在检索时机，确定性放在检索执行。

## 4.14 引用溯源如何保证正文和前端来源一致？
> **可能追问：**有引用就证明回答正确吗？不代表。还要看被引用原文是否支持那句话、是否遗漏条件。引用提供核查入口，不能替代答案依据检查；跨多次工具调用也要保持来源 ID 不冲突。
> **参考回答：**工具取得父块后，为本轮来源分配 source_id，并构造包含 product_id、clause_name、section_path、content 的来源字典。同一份来源关系一方面交给模型，要求正文按 ID 引用；另一方面通过 custom 事件发送给前端。
> 前端把 [ref-001] 之类标记转换为可点击编号，列表展示 clause_name，不把 ref-001 当文件名。引用原文直接来自父块，而不是让模型重新生成一段“原文”。来源可能早于或晚于部分文本到达，因此展示逻辑需要根据正文与来源映射共同更新。

## 4.15 刷新页面后引用为什么还能展示？custom 事件不是已经发送了吗？
> **可能追问：**为什么不用 thread_id 作为来源的唯一键？同一个会话会有多次条款问答，只存一份会使历史引用错绑。thread_id 定位会话，AI 消息 ID 定位回答，source_id 定位该回答的具体依据。
> **参考回答：**custom 是运行过程中的事件，不会因为发送到前端就自动成为 Graph State。实时页面能显示，只说明这次连接拿到了来源；历史接口要恢复它，需要另一个持久化动作。
> 我们在处理流时收集 additional_info，识别本轮最终可见 AI 消息的 ID，把来源存成以消息 ID 为键的字典，再写入 State。查询历史时，取消息列表并按 AI 消息 ID 找对应来源。Reducer 合并的是不同消息的记录，避免新一轮覆盖上一轮。

## 4.16 如何判断 RAG 效果，出了错误从哪里排查？
> **参考回答：**我会准备与保险业务对应的问题集：同义口语问法、专业名称、条款编号、条件和例外、多产品对比、多轮指代，以及条款中没有答案的问题。每条样例标注目标产品、应命中的章节和答案要点，而不是只准备几个演示问题。
> 排查按链路进行：原 PDF 是否有依据；解析和优化是否保留；切分归属是否正确；product_id 和 query 是否正确；候选有没有召回；重排是否前置；回查是否丢失或重复；最后再看 Prompt 与回答。检索看 Recall@K、MRR 等相关指标，生成看依据支持、条件完整和引用正确，端到端再看延迟与工具调用量。
> **可能追问：**命中文档但回答仍错怎么办？先看上下文是否缺少限定条件，再看问题理解和提示约束。没有召回与召回后误读是两类问题，不能用同一个“准确率”掩盖。

# 5. Agent 专题面试题与参考答案

## 5.1 已经有 LangChain create_agent，为什么还要 LangGraph？
> **参考回答：**create_agent 适合快速构建模型与工具循环，保险顾问子 Agent 就复用了它。但整个客服不只有一个任务，还要做闲聊、保险咨询、理赔和转人工的路由，并管理业务切换和共享状态，因此需要更明确的外层编排。
> 我们用 LangGraph 主图表达这些业务边界，再把 create_agent 生成的保险顾问作为子节点接入。两者不是二选一：LangChain 提供方便的 Agent 和组件，LangGraph 提供可控制的工作流结构。
> **可能追问：**是不是每个节点都调用大模型？不是。寒暄规则、状态更新、业务校验和数据库写入可以是普通程序。节点的含义是执行单元，不是一次 LLM 调用。

## 5.2 为什么不把所有工具交给一个大 Agent？
> **可能追问：**多个 Agent 会不会并行讨论？本项目核心是路由式编排，一次任务进入对应工作流，不等于所有 Agent 同时回答。需要比较方案时也不必先引入角色辩论。
> **参考回答：**保险选购与理赔咨询的目标不同，所需上下文和工具也不同。一个大 Agent 同时看到大量工具和所有业务规则，工具选择与提示约束会变得难以管理，也不利于不同业务同事独立维护。
> 我们的拆分是主图按意图选工作流，子 Agent 在限定范围内完成任务。但不会把每个动作都拆成 Agent，例如候选查询和条款检索保留为保险顾问工具。这样既能隔离职责，也避免为了“多 Agent”增加无意义协作。

## 5.3 意图识别如何实现，为什么要结合上一轮状态？
> **参考回答：**先用规则处理明确的简短寒暄，再由模型返回受约束的结构化路由结果。识别输入不仅有当前用户文本，还包含上一轮工作流和最近的可见回复，因为很多追问本身不完整。
> 例如顾问刚问预算，用户回答“两万以内”，如果只看这一句很难识别；结合上一轮保险推荐，就能继续该任务。另一方面，用户明确问理赔进度时，应切换到理赔，不能因为上一轮推荐就一直锁定推荐。结构化输出限制合法工作流名称，执行失败时走兜底。
> **可能追问：**结构化输出能保证意图正确吗？只能约束输出形状和候选值，语义仍需用多轮样例验证。对“你好，我想查保单”也不能用包含“你好”的粗糙规则提前拦截业务。

## 5.4 active_workflow 和 previous_workflow 为什么要区分？
> **可能追问：**所有业务变量都放主 State 吗？不是。主 State 放消息、路由等跨工作流信息；只在闲聊中读写的 chitchat_count 放在子 State。共享需求决定位置，而不是为了省事把所有字段集中。
> **参考回答：**active_workflow 表示当前激活的任务，previous_workflow 保存切换前的任务。路由处理新一轮输入时，先记住原来的 active_workflow，再写入本轮识别结果，这样子工作流才能判断是否刚刚从其他业务切入。
> 例如用户从保险咨询切到闲聊，闲聊计数需要重新开始；如果一直在闲聊，则继续累计。字段表达的是工作流转移关系，不是模型自己生成的随意标签。

## 5.5 State、Context、config 和 app.state 有什么区别？
> **参考回答：**State 是任务运行中变化的数据，例如 messages、工作流状态和消息引用关系，可通过 Checkpointer 持久化。Context 是本次调用由应用传入的运行时信息，例如 user_id。config 中的 thread_id 用于选择会话检查点。
> FastAPI 的 app.state 则保存应用级共享对象，比如启动时构建的主 Graph，与 LangGraph State 不是同一种东西。四者名字相似，但生命周期和用途不同：任务状态、调用上下文、执行配置、应用资源。
> **可能追问：**为什么不让模型填 user_id？身份不是推理结果。工具从 runtime.context 取得服务端传入的身份，再由业务逻辑校验资源归属；模型只提供业务参数。

## 5.6 Reducer 的作用是什么？引用字典为什么需要它？
> **可能追问：**消息 Reducer 是否只是列表相加？并不只是。基于消息 ID 的更新语义很重要，否则同一消息的更新可能变成重复记录。需要根据字段语义选合并方式。
> **参考回答：**节点通常返回 State 的部分更新，Reducer 决定旧值和新值如何合并。工作流名称通常覆盖更新；消息使用消息合并规则；additional_info 则需要保留不同 AI 消息对应的来源，而不��整张字典被新一轮替换。
> 例如已有 {消息A: 来源A}，本轮更新 {消息B: 来源B}，合并后两条都要在。Reducer 应返回合并结果，不能把原地 update 的返回值当作字典。对于同一消息内部的多个来源，还要明确采用整体替换还是继续合并，不能以为外层合并会自动处理任意嵌套。

## 5.7 父图和子图如何共享状态？闲聊次数会串到别的会话吗？
> **可能追问：**同一用户开两个会话呢？它们有不同 thread_id，闲聊次数和消息应分别计算。用户 ID 用于归属，会话 ID 用于上下文，两者不能互相替代。
> **参考回答：**直接把已编译子图作为父图节点时，共有字段可以进行状态映射，子图更新按父图对应的合并规则写回。我们共享消息和工作流信息，闲聊次数则留在子图自己的 State。
> 子图配置与父图 Checkpointer 协同，私有状态由对应子图的检查点命名空间和会话保存。状态隔离依赖正确的 thread_id 和子图持久化配置，而不是在 Python 全局变量中做一个计数器。

## 5.8 工具调用到底是谁执行，模型会直接访问数据库吗？
> **可能追问：**工具描述怎么写？说明什么时候使用、需要哪些条件、结果代表什么。例如最低保费只是参考筛选信息，不是用户正式报价；这会影响模型如何解释返回值。
> **参考回答：**模型接收到的是工具名称、说明和参数结构。它返回工具调用信息后，由框架把调用分发到我们注册的 Python 函数；函数执行查询或业务操作，再把结果作为工具消息交回模型。模型不持有数据库连接，也不直接生成 SQL 执行。
> 例如候选工具调用 ProductService，Service 按险种组织查询，Repository 执行带条件和数量限制的 SQL。工具层只负责把 Agent 调用适配到业务能力，避免复制一套业务规则。

## 5.9 候选筛选为什么不让模型从全部产品里自己选？
> **参考回答：**先用程序根据分类、价格条件和数量限制缩小集合，可以减少上下文长度，也让明确筛选条件由确定性逻辑执行。模型再结合年龄、职业、需求和候选特征组织组合，而不是面对整个产品表自由发挥。
> 分层上，Repository 提供单次条件查询，Service 负责循环不同险种和组装结果。工具复用 Service。这样商城接口与 Agent 使用同一套业务能力，数据库访问细节不会混进模型提示词。
> **可能追问：**只凭最低保费能确定适合或买得起吗？不能。它只用于候选粗筛，实际价格依赖定价条件，适用性还要看产品条件和用户信息。回答时要区分候选、建议预算和具体测算。

## 5.10 如何防止 Agent 伪造产品、金额或保存错误数据？
> **可能追问：**给模型一句“不要编造”够不够？不够。提示约束、工具数据、业务校验和确认交互承担不同职责，需要一起工作。
> **参考回答：**先把事实来源分清：产品 ID 和属性来自查询工具，条款来自 RAG，保费来自测算接口，用户身份来自 Context。Prompt 负责告诉模型如何使用这些来源，但真正的 ID、归属和数据约束由业务 Service 校验。
> 保存工具采用结构化参数，业务层校验产品存在性、字段范围和方案结构，在事务中保存方案及明细。工具返回真实保存结果后，模型才能说明已保存。用户点击确认也不能替代后端参数和归属检查。

## 5.11 方案为什么要用 interrupt，而不是让 AI 问一句“确认吗”？
> **可能追问：**刷新后确认框还在吗？历史接口读取检查点中的未完成中断并恢复卡片。不能只依靠当前浏览器内存记住它。
> **参考回答：**一句“确认吗”只是文本，没有可靠表示任务已经暂停，也没有绑定待保存内容。interrupt 则在工作流中形成明确暂停点，将方案和允许的动作交给前端，等待用户决策。
> 用户确认后，前端在同一个 thread_id 提交 decision，服务端使用 Command(resume=...) 恢复。保存发生在批准之后；拒绝时返回拒绝信息或原因，让后续对话调整方案，而不是仍然写库。这让确认成为程序状态，而不是依赖模型记住一句话。

## 5.12 interrupt 恢复后代码会从暂停行继续吗？写操作放哪里？
> **可能追问：**用户点击两次确认怎么办？这属于同一业务动作的重复请求问题。应检查待确认状态并让写入具备明确的重复处理语义，而不是让模型判断两次是否相同。
> **参考回答：**不能把恢复理解成普通协程在内存中从原地继续。恢复执行时，包含中断的节点可能从头执行，中断调用再取得恢复值。因此中断前的操作要考虑重入，不能在前面先把方案保存一次，后面再问是否确认。
> 本项目把数据库写入放在取得批准决定之后，把待确认内容准备与真实写入分开。业务结果由 Service 返回；对于有重复提交风险的写操作，还要由业务层定义幂等规则，Checkpointer 不等于外部数据库操作天然只执行一次。

## 5.13 Checkpointer 与 chat_thread 表有什么区别？
> **可能追问：**删除会话要删什么？既要删会话元数据，也要清理该 thread_id 的检查点。两类存储操作不能因为都在 PostgreSQL 就被描述成天然同一个事务。
> **参考回答：**chat_thread 是商城的会话目录，保存标题、用户归属和时间，方便列表、重命名等操作。Checkpointer 保存 Graph 的消息和执行状态，用于恢复对话与中断。一个负责业务管理，一个负责运行上下文。
> 发起对话、查历史或删除时先校验 chat_thread 归属，再使用它的 ID 作为 thread_id 操作 Graph 状态。aget_state 返回的是 StateSnapshot，不只是一个消息数组；其中 values 是状态值，next、tasks 等描述执行进度和任务信息。

## 5.14 会话持久化为什么使用 PostgreSQL，而不是进程内存？
> **可能追问：**持久化是不是长期记忆？这里主要是会话级状态记忆。跨会话用户画像、长期偏好与知识库是另外的数据用途，不能因为落盘就把它们都称为同一种记忆。
> **参考回答：**服务需要跨请求和重启延续会话，内存保存只适合单进程临时使用。项目已有 PostgreSQL，接入 AsyncPostgresSaver 后可以把消息与执行状态持久化，并按 thread_id 恢复，不必自己重新实现整套 Graph 状态保存协议。
> 业务 ORM 使用 SQLAlchemy/asyncpg，Checkpointer 使用 psycopg 的异步连接池；它们可以连接同一数据库，但不是同一个客户端。连接池在生命周期中打开和关闭，Saver 在异步启动阶段创建，避免导入模块时依赖尚未运行的事件循环。

## 5.15 SSE 怎么对接 Agent，为什么不把完整 Graph 事件发给前端？
> **可能追问：**为什么不用 WebSocket？当前是一次请求后持续返回服务端生成内容，SSE 与需求匹配。采用 SSE 不代表已经自动实现业务断点续传，网络重连与恢复一次 Agent 执行是不同问题。
> **参考回答：**我们使用统一 POST 对话接口接收 message 或 decision，后端遍历 astream_events 的 v3 事件流，把需要展示的文本和 custom 数据映射为 SSE 的 message、additional_info、interrupt、done。
> Graph 内部包含主图、子图、工具与控制信息，前端不应与这些实现细节耦合。适配时还要避免把路由模型的结构化输出当作用户回复。采用 POST 流式请求时，前端通过 fetch 读取响应流，并不是原生 EventSource 的 GET 用法。

## 5.16 文本、工具事件和子图消息如何避免丢失或错绑？
> **参考回答：**接入子图后，不能只按照根图消息去处理所有输出。我们在统一事件适配中识别事件来源和数据类型，将可见文本累积到本轮回答，将来源信息累积到本轮附加信息，不把 ToolMessage 直接展示给用户。
> 如果使用多个异步事件迭代器，必须按所用库的订阅和上下文约定消费；合并流也要在它的有效上下文中迭代，不能先完全消费一种流再假设其他事件仍可读取。当前可以通过统一解析 v3 事件来减少多路合并的复杂度。done 应在需要的事件处理和状态关联完成之后发送。
> **可能追问：**为什么不能看到第一个 AIMessage ID 就绑定来源？一轮可能有工具调用前的消息和最终回答，ID 用途必须明确。要将来源绑定到前端展示的对应回答，不能误绑到用于发起工具调用的消息。

# 6. 综合场景题：把 RAG、Agent 与商城业务串起来

## 6.1 用户说“预算两万，给我推荐”，Agent 应该如何处理？
> **参考回答：**不能把预算直接转换成产品列表。先通过对话补齐会影响推荐的信息，再调用候选工具取得真实产品，围绕用户需求组织险种和产品组合。推荐理由应对应候选产品的特征，价格表达区分建议预算与实际测算。
> **场景：**用户只提供预算，没有说明年龄、职业和保障需求。
> **进一步展开：**用户追问保障细节时再调用对应产品的条款工具；用户认可后进入确认和保存。这不是一条固定“每轮查产品、每轮查条款”的流水线，而是主业务目标明确、工具调用按需发生的 Agent 流程。

## 6.2 用户说“这款和刚才那款，免赔额有什么区别”？
> **场景：**当前会话出现过两个产品，问题包含指代和比较。
> **参考回答：**先从上下文确定两个产品 ID，分别以各自 ID 检索免赔额条款。给模型的上下文保留产品和来源身份，回答时按产品列出约定、适用范围与差异，并分别引用原文，避免把两个产品的条件拼成一份结论。
> **进一步展开：**如果指代不明确应先澄清；如果一侧没有足够依据，要明确那一侧尚不能比较。该题可以同时讲路由上下文、Agent 生成查询、product_id 过滤、父块补全和引用对应。

## 6.3 用户从方案咨询突然问“我的理赔到账了吗”？
> **场景：**上一轮还在聊推荐，现在询问个人理赔进度。
> **参考回答：**路由应识别明确的新业务意图，进入理赔工作流。到账或审核状态来自用户自己的理赔记录，而不是条款向量库；需要时结合保单和理赔 ID 定位记录。若用户继续问某种材料为什么要提交，再查询指引或相应条款。
> **进一步展开：**这体现三种数据协作：会话上下文帮助理解指代，业务数据库回答进度，RAG 解释条款。不能因为理赔也与保险有关，就让原来的推荐工具集硬处理所有售后任务。

## 6.4 模型说“方案已经保存”，但页面没有方案，如何定位？
> **参考回答：**从工具链检查：是否真的产生保存调用、是否触发确认、是否收到批准决定、Service 是否执行并提交事务、返回的方案 ID 和 user_id 是什么。再核对页面查询的用户和接口，区分模型提前宣称成功、业务执行失败和前端查询不一致。
> **场景：**用户看到成功文案，却查不到对应记录。
> **进一步展开：**回答成功应基于工具返回，而不是仅根据用户说“好”。这道题的重点是模型输出不等于业务事实；可以用工具调用 ID、thread_id 和业务结果 ID 关联排查。

## 6.5 命中了免赔额章节，却把“不适用”答成了“适用”，怎么分析？
> **场景：**检索结果主题正确，但答案漏掉否定或适用条件。
> **参考回答：**先核对解析后的文本是否保留否定词，确认结构优化没有改写含义，再看子块回查到的父块是否包括相关条件和例外。如果依据完整，再检查模型是否混用了别的产品、是否把示例当成普遍规则、引用是否真正支持结论。
> **进一步展开：**仅提高向量相似度或增大 TopK 未必解决此类错误。它可能是解析质量、上下文组装或依据使用问题，而不是召回问题。验证时把“包含关键词”与“完整支持答案”区分开。

## 6.6 服务重启后还能聊天，为什么这不等于所有任务都自动恢复？
> **参考回答：**Checkpointer 提供恢复所需的状态和执行信息，但仍需要应用使用正确 thread_id 发起后续调用，并正确处理挂起中断。数据库写入或外部业务请求是否重复执行，也要遵循各自的事务和幂等语义，不能笼统说“有检查点就不会出问题”。
> **场景：**会话状态已经持久化，面试官追问执行可靠性。
> **进一步展开：**项目中可以具体演示两类恢复：普通会话继续读取历史上下文；未确认方案重新展示中断卡片，再提交 resume。它们比抽象宣称“支持容灾”更能说明掌握了机制。

## 6.7 如何评价一次端到端对话是不是成功？
> **参考回答：**先看任务是否完成：推荐使用了真实候选，条款回答有正确产品的依据，保存经过确认并返回业务 ID。再看交互是否一致：文本与卡片对应，引用可打开，刷新后历史与待确认状态正确。
> **场景：**顾问回答很流畅，是否就代表链路正确？
> **进一步展开：**性能分开统计首个可见文本时间、总响应时间、模型调用次数、检索与重排耗时。SSE 让文本不必等全部生成后才展示，但不能自动缩短模型思考、工具查询或重排本身的时间。不要把流式输出直接等同于模型推理加速。

## 6.8 如果让你介绍最难的两个问题，你怎么回答？
> **场景：**面试官希望听到具体经历，不是再听一遍技术栈。
> **参考回答：**第一个讲知识粒度：条款局部命中与完整条件之间的矛盾，如何通过结构处理、父子块和产品过滤解决，再通过引用查看原文验证。第二个讲任务状态：实时 custom 事件与持久会话状态不同，如何关联到 AI 消息，以及确认流程如何通过 interrupt 跨请求恢复。
> **进一步展开：**每个问题讲清原始现象、定位过程、设计选择和可展示结果。不要把“用了 LangGraph”“用了 Milvus”本身作为难点；难点是它们在业务链路中解决了什么具体矛盾。

# 7. 面试练习与复习路径

## 7.1 准备一场十分钟项目演示
第1分钟：介绍商城整体业务与个人分工。第2—3分钟：画出前端、FastAPI、主 Graph、业务工具、PostgreSQL 和 Milvus 的关系。第4—6分钟：用产品咨询与条款追问演示 RAG 数据流。第7—8分钟：演示方案确认、保存以及刷新后的会话恢复。第9—10分钟：选择父子块或事件持久化讲清一个设计取舍。

## 7.2 每一条简历职责准备四份证据
一段业务输入：例如“这款保险的免赔额能累计抵扣吗”。一条调用链：指出 Router、Graph、Tool、Retriever 和数据库的关系。一份中间结果：展示 product_id、召回块、父块和来源映射。一个设计理由：说明为什么这样分层、为什么采用该检索策略。
不要求把源码背下来，但应该能解释关键数据的来路和去向。尤其要分清三个 ID：user_id 决定业务归属，thread_id 决定会话上下文，AI 消息 ID 决定引用绑定到哪条回答；parent_id 与 source_id 则分别连接父子块和展示依据。

## 7.3 自测：不看笔记能否回答这些问题
能否用完整业务而不是技术名词介绍商城？能否画出离线入库和在线检索两条链？能否解释产品查询与条款检索为什么走不同存储？能否说明主图和子 Agent 各自控制什么？能否演示一次 interrupt 的触发和恢复？能否解释实时事件为何还需要写入 State？
回答时先给一句结论，再沿项目链路展开，最后说明取舍。例如“子块负责定位、父块负责提供上下文”，接着讲 parent_id、去重和批量回查，最后讲父块长度与上下文成本。这样既清楚，也方便面试官继续追问。
