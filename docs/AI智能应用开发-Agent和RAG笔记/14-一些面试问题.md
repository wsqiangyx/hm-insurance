# 一、项目介绍：《安心保》AI保险顾问

## 1.1 项目概述
**项目名称：**安心保 — 在线保险商城 + AI智能保险顾问
**一句话介绍：**基于大模型、RAG和Agent技术的智能保险商城，AI保险顾问能够协助用户选购保险、解释条款、推荐保险组合方案、指引理赔，支持流式对话和多轮上下文记忆。

## 1.2 项目背景
保险行业产品复杂、条款专业，普通用户面对众多保险产品（百万医疗险、重疾险、寿险、意外险等）往往存在以下痛点：
- 不知道自己应该配置哪几类保险
- 每类保险选哪个产品，缺乏专业判断
- 保险条款晦涩难懂，不知道哪些内容影响理赔
- 传统人工保险顾问成本高、覆盖有限、7×24小时无法响应
因此，《安心保》商城在提供保险产品浏览和交易的基础上，集成了AI智能保险顾问，通过大模型 + RAG + Agent技术，为用户提供专业、准确、7×24小时的保险咨询服务。

## 1.3 我的职责
- 负责 agent-service 后端整体架构设计与开发，基于 Python FastAPI 异步框架
- 主导 AI 保险顾问 Agent 的设计与实现，包括 LangGraph 多 Agent 编排、工具调用、会话记忆
- 负责 RAG 知识库的构建与优化，包括保险条款 PDF 解析、父子块切分策略、Milvus 混合检索
- 实现 SSE 流式对话接口，提升用户交互体验
- 设计保险方案推荐链路，实现从候选产品查询到方案生成、保存的完整闭环

## 1.5 项目核心成果
- 实现了基于 LangGraph 的多 Agent 编排架构，支持意图路由（闲聊/保险推荐/理赔咨询/转人工），不同意图路由到独立子工作流

# 二、项目架构介绍

## 2.1 整体系统架构
《安心保》系统采用前后端分离架构，整体分为两大模块：

| 模块 | 技术栈 | 职责 |
| --- | --- | --- |
| **frontend（前端）** | React + Ant Design | 保险商城页面、产品浏览、登录注册、智能客服对话框 |
| **agent-service（后端）** | Python FastAPI + LangGraph + LangChain | 传统保险业务（用户/产品/方案/保单/理赔）+ AI保险顾问（意图路由/RAG问答/工具调用/方案推荐） |
后端 agent-service 内部采用分层架构：
- **接入层（Router）**：FastAPI 路由，接收 HTTP 请求，参数校验，依赖注入
- **业务层（Service）**：业务逻辑编排，事务控制，调用 Repository 和 Agent
- **数据层（Repository）**：数据库访问，SQLAlchemy 异步 ORM
- **AI 层（Agents）**：LangGraph 主 Graph 编排、子 Agent、工具定义、RAG 检索
- **基础设施层（Infra）**：数据库连接池、Checkpointer、向量数据库客户端
- **核心层（Core）**：配置管理（pydantic-settings）、结构化日志（structlog）

## 2.2 AI 保险顾问 Agent 架构
AI 保险顾问采用 **LangGraph 多 Agent 编排架构**，由一个主 Graph（Orchestrator）负责意图识别和工作流路由，不同意图分发到独立的子 Agent / 子 Graph 处理。

### 主 Graph 结构

| 节点 | 职责 |
| --- | --- |
| **route（路由节点）** | 意图识别，判断用户消息属于闲聊/保险推荐/理赔咨询/转人工/无法识别，路由到对应工作流 |
| **chitchat（闲聊节点）** | 处理闲聊，最终引导用户到保险产品咨询 |
| **recommendation_plan（保险推荐节点）** | 保险方案咨询和推荐子 Agent，支持工具调用（查产品、算保费、保存方案）和 RAG 条款问答 |
| **claim（理赔咨询节点）** | 理赔咨询子 Agent，查询保单、解释条款、说明理赔流程 |
| **human_handoff（转人工）** | 复杂问题转人工客服 |
| **fallback（兜底）** | 意图无法识别时，引导用户明确需求 |

### State 设计
主 Graph 的 State 继承自 LangChain 的 MessagesState，包含：
- **messages**：跨工作流共享的会话消息历史
- **previous_workflow**：上一轮对话激活的工作流（用于上下文延续）
- **active_workflow**：本轮对话激活的工作流

### 会话记忆持久化
使用 LangGraph 的 **PostgreSQL Checkpointer（AsyncPostgresSaver）** 实现会话状态持久化：
- 每次与 Agent 交互产生一次 State 快照，按 thread_id（会话ID）存储
- 服务重启后，通过 thread_id 可恢复完整对话历史
- Checkpointer 使用独立的 psycopg 异步连接池（与 SQLAlchemy 的 asyncpg 驱动隔离）
- 删除会话时，同时删除业务表记录和 Checkpointer 中的全部 Checkpoint

## 2.3 RAG 条款问答架构
保险条款问答是项目的核心能力，采用 **Agentic RAG** 架构（检索封装为 Tool，由 Agent 自主决定何时检索），而非传统的 2-Step RAG（每次提问都强制检索）。

### 为什么选择 Agentic RAG

| 对比维度 | 2-Step RAG | Agentic RAG（本项目采用） |
| --- | --- | --- |
| 检索时机 | 每次提问都检索 | Agent 自主判断是否需要检索 |
| 闲聊场景 | 浪费检索开销，可能引入无关上下文 | 不触发检索，直接由模型回答 |
| 复杂问题 | 单次检索可能不够 | 支持多次检索、多轮迭代 |
| 查询生成 | 直接用用户原问题检索 | Agent 可根据上下文生成更精准的检索查询 |

### 知识库构建（离线阶段）
**1. 文档加载：MinerU 解析保险条款 PDF**
- 保险条款 PDF 结构复杂（多栏、复杂表格、图文混排），普通 PyPDF 解析效果差
- 使用 MinerU（上海AI实验室开源）进行高精度 PDF 解析，输出结构化 Markdown
- 支持 OCR，可处理扫描件类型的条款文档
- 支持 Precision（精准解析，需 Token）和 Flash（轻量解析，免登录）两种模式
**2. 文档切分：父子块切分策略（核心创新点）**
保险条款切分面临检索精度与语义完整度的矛盾：
- 块太大 → 噪音多，检索精度下降
- 块太小 → 丢失上下文，语义不完整
解决方案：**父子块双层结构**

| 块类型 | 存储位置 | 作用 | 切分方式 |
| --- | --- | --- | --- |
| **父块（Parent Chunk）** | PostgreSQL | 保存完整条款章节，保证语义完整度，最终返回给 LLM 作为上下文 | 按条款标题结构（Markdown 标题层级）切分，每块对应一个条款章节 |
| **子块（Child Chunk）** | Milvus 向量库 | 用于相似度检索，保证检索精度，记录 parent_id 关联父块 | 对父块进一步使用 RecursiveCharacterTextSplitter 递归切分，保留所属标题信息 |
检索流程：用户问题 → Milvus 检索子块（TopK）→ 根据子块的 parent_id 去 PostgreSQL 查询完整父块 → 父块内容作为上下文传给 LLM 生成答案
**3. 产品维度过滤**
- 保险商城包含多款产品，同类型产品的条款有很多相似内容（如都有等待期、免责条款）
- 子块 metadata 中记录 product_id，检索时以 product_id 作为过滤条件
- 确保用户询问 A 产品时，只检索 A 产品的条款，避免跨产品混淆
**4. 向量化与存储**
- 向量模型：Qwen3-Embedding（本地 Ollama 部署）或 DashScope Embeddings
- 向量数据库：Milvus 2.6，支持稠密向量 + 稀疏向量（BM25）混合检索
- 子块结构：id、parent_id、content、product_id、稠密向量、稀疏向量

### 在线问答阶段
1. 用户提问进入保险推荐子 Agent
1. Agent 判断是否需要检索条款（如询问"这款产品的等待期是多久"→ 需要检索）
1. Agent 调用检索 Tool，传入查询词和 product_id
1. Milvus 混合检索（稠密+稀疏）返回 TopK 子块
1. 根据子块 parent_id 批量查询 PostgreSQL，获取完整父块内容
1. 父块内容 + 用户问题 → 大模型生成答案，并附带来源条款信息

## 2.4 保险方案推荐链路
保险方案推荐是 Agent 工具调用的典型应用，完整链路如下：
1. **用户画像采集**：Agent 通过多轮对话收集用户年龄、职业、预算、保障需求等信息
1. **候选产品查询**：Agent 调用 query_candidate_products 工具，按险种（medical/critical_illness/life/accident）和预算条件查询候选产品，每个险种最多返回指定数量
1. **方案生成**：大模型根据用户画像和候选产品，选择合适产品组合，分配预算，为每款产品生成推荐理由
1. **方案保存**：Agent 调用 save_insurance_plan 工具，将方案（含用户画像、方案名称、整体说明、方案项列表）保存到 PostgreSQL
**工具调用安全设计：**
- 使用 LangChain 的 Context 机制传递当前用户 ID（InsuranceAgentContext）
- user_id 不作为工具参数暴露给大模型，而是通过 ToolRuntime 注入，防止大模型伪造用户 ID
- 保存方案时，工具内部从 runtime.context.user_id 获取当前用户，确保方案归属正确
- 使用 FastAPI 原生的 EventSourceResponse 和 ServerSentEvent
- Agent 调用使用 astream_events(version="v3") 获取异步事件流
- 只提取 AI 消息的文本增量（message.text），逐片段 yield 给前端
- 最后发送 event: done 标识结束
- EventSourceResponse 自动设置 text/event-stream、Cache-Control: no-cache 等响应头，并支持断线重连

## 2.6 数据存储设计

| 存储 | 存储内容 | 关键表/集合 |
| --- | --- | --- |
| **PostgreSQL** | 业务数据 + 会话状态 | users（用户）、products（保险产品）、chat_threads（会话）、insurance_plans（保险方案）、insurance_plan_items（方案项）、parent_chunks（RAG父块）、checkpoints/blobs/writes（LangGraph Checkpointer 自动建表） |
| **Milvus** | RAG 子块向量 | 子块集合：id（主键）、text（内容）、parent_id、product_id、dense（稠密向量）、sparse（稀疏向量） |
| **MinIO** | Milvus 依赖的对象存储 | Milvus 原始数据文件 |

| 没有量化成果 | 无法判断项目价值和个人贡献 | 尽量量化：检索准确率提升X%、响应时间降低X%、支撑X并发、节省X成本 |
| 写了"微调大模型"但只是跑了demo | 面试官会深挖微调细节，容易露馅 | 如果只是了解，写"了解大模型微调基本原理（LoRA/SFT）"即可，不要夸大 |
| 项目描述像教程笔记 | 看不出个人思考和创新 | 突出你做的技术决策、遇到的难点、创新的解决方案（如父子块切分策略） |

# 四、常见面试题与参考答案（《安心保》项目相关）

## 4.1 RAG 相关高频题

### Q1：介绍一下你们项目的 RAG 架构，为什么这样设计？
**考察点：**RAG 整体理解、架构设计能力、技术选型理由
**参考答案：**
> 我们项目的 RAG 采用 **Agentic RAG** 架构，而不是传统的 2-Step RAG。整体分为离线知识库构建和在线问答两个阶段。
> **离线阶段：**
> 1. **文档加载**：保险条款是复杂 PDF（多栏、复杂表格、图文混排），我们用 MinerU 做高精度解析，输出结构化 Markdown。传统 PyPDF 对复杂表格和多栏解析效果很差，MinerU 支持 OCR 和版面分析，更适合保险条款。
> 2. **文档切分**：这是我们项目的核心设计点——**父子块切分策略**。保险条款切分面临检索精度和语义完整度的矛盾：块太大噪音多检索不准，块太小又丢失上下文。我们的方案是：父块按条款标题结构切分（每个条款章节一个父块），存入 PostgreSQL 保证语义完整；子块对父块进一步用 RecursiveCharacterTextSplitter 递归切分，存入 Milvus 保证检索精度。子块记录 parent_id，检索到子块后通过 parent_id 查完整父块，再交给大模型。
> 3. **向量化与存储**：用 Qwen3-Embedding 生成向量，存入 Milvus 2.6。我们同时存稠密向量和稀疏向量（BM25），做混合检索。另外，子块 metadata 里带 product_id，检索时按产品过滤，避免用户问 A 产品却检索出 B 产品的条款。
> **在线阶段：**
> 我们没有用传统的"每次提问都检索"的 2-Step RAG，而是把检索封装成一个 Tool，交给 Agent 自主决定何时检索。这样做的好处是：闲聊场景不需要检索，避免无效检索开销和无关上下文干扰；复杂问题 Agent 可以多次检索、迭代优化查询词。
> 检索流程：Agent 调用检索 Tool → Milvus 混合检索返回 TopK 子块 → 根据 parent_id 批量查 PostgreSQL 拿完整父块 → 父块内容 + 用户问题交给大模型生成答案，并附带来源条款信息。

### Q2：RAG 的文档切分策略有哪些？你们为什么用父子块？
**考察点：**RAG 切分策略深度理解、技术权衡能力
**参考答案：**
> 常见的文档切分策略有以下几种：
> 1. **固定长度切分**：按固定字符数切分，简单粗暴，但容易切断语义，不适合结构化文档。
> 2. **递归字符切分**（RecursiveCharacterTextSplitter）：按换行、段落、句子逐级递归切分，尽量保持语义完整，是 LangChain 默认推荐的通用方案。
> 3. **基于文档结构切分**（MarkdownHeaderTextSplitter）：按 Markdown 标题层级切分，每个标题下的内容为一个块，适合结构化文档，能保留章节上下文。
> 4. **语义切分**：根据语义相似度切分，语义相近的句子放在一起，需要额外的模型计算，成本较高。
> 5. **父子块切分**（Parent-Child Chunking）：大块（父块）保证语义完整，小块（子块）保证检索精度，检索到子块后返回父块。
> **我们为什么用父子块：**
> 保险条款有两个特点：一是结构清晰，按章节条款组织，适合按标题切分；二是部分条款内容很长（如免责条款、健康告知），如果整个章节作为一个块，语义完整但噪音太大，检索精度会下降。
> 我们的方案结合了"基于结构切分"和"递归切分"的优点：父块按标题结构切分，保证条款级别的语义完整；子块对父块递归切分，保证检索精度。检索时用子块做相似度匹配（精准），但返回给大模型的是完整父块（语义完整），两者通过 parent_id 关联。
> 这样既解决了大块检索不准的问题，又避免了小块丢失上下文的问题，是针对保险条款这种"结构清晰但部分内容长"的文档的最优解。

### Q3：RAG 检索效果不好怎么优化？你们做了哪些优化？
**考察点：**RAG 优化经验、问题排查能力
**参考答案：**
> RAG 检索效果不好，通常从几个维度排查和优化：
> **1. 文档处理层面：**
> - **解析质量**：如果 PDF 解析就丢内容、乱序，后面切分和检索都白搭。我们用 MinerU 替代 PyPDF，解决了复杂表格和多栏解析的问题。
> - **切分策略**：块太大或太小都会影响检索。我们用父子块策略，子块控制在合适大小（200-500 token），同时通过父块保证上下文完整。
> - **元数据增强**：给块加上标题、章节路径、产品 ID 等元数据，检索时可以做过滤，也能帮助大模型理解上下文。
> **2. 检索层面：**
> - **混合检索**：纯向量检索对关键词匹配不好（如保险产品名、专业术语），我们用稠密向量 + 稀疏向量（BM25）混合检索，兼顾语义匹配和关键词匹配。
> - **查询改写**：用户的问题可能口语化、不完整，Agent 可以根据上下文改写查询词，生成更适合检索的查询。我们的 Agentic RAG 架构天然支持这一点。
> - **多路召回**：可以同时用多种检索方式（向量、关键词、知识图谱），合并去重后再重排。
> - **过滤条件**：我们按 product_id 过滤，确保只检索当前产品的条款，避免跨产品混淆，这对多产品知识库非常重要。
> **3. 重排层面：**
> - 检索回来的 TopK 结果，可以用 Reranker 模型（如 BGE-Reranker、Cohere Rerank）做二次排序，提升相关性。
> **4. 生成层面：**
> - **Prompt 优化**：明确要求大模型基于检索内容回答，不知道就说不知道，不要编造。
> - **引用溯源**：要求答案附带来源条款，既提升可信度，也方便验证。
> - **多轮迭代**：Agentic RAG 支持如果第一次检索结果不够，Agent 可以调整查询词再次检索。
> **我们项目具体做的优化：**MinerU 高精度解析、父子块切分、混合检索、产品维度过滤、Agentic RAG 自主检索、引用溯源。

### Q4：向量数据库为什么选 Milvus？和其他向量库比有什么优势？
**考察点：**向量数据库选型、技术对比能力
**参考答案：**
> 我们选 Milvus 主要基于以下几点考虑：
> **1. 功能完整性：**Milvus 是一个专业的向量数据库，不是简单的向量库插件。它支持：
> - 稠密向量 + 稀疏向量混合检索（我们项目用了 BM25 稀疏向量）
> - 标量字段过滤（我们用 product_id 做过滤）
> - 多种索引类型（HNSW、IVF_FLAT 等）
> - 分区、分片、水平扩展
> 像 Chroma、FAISS 这些更偏向轻量级库，功能相对简单，不支持稀疏向量和复杂过滤，适合原型开发，不太适合生产环境。
> **2. 性能和扩展性：**Milvus 是分布式架构，支持海量向量（十亿级）的低延迟检索，支持独立扩展计算节点和存储节点。我们的保险条款虽然目前数据量不大，但未来产品增多、条款更新频繁，Milvus 的扩展性有保障。
> **3. 生态和成熟度：**Milvus 是 Zilliz 开源的，2019 年就开源了，社区活跃，生产案例多，LangChain 原生支持。相比 Pinecone（闭源、SaaS only、成本高），Milvus 可以自建，数据可控，成本更低。
> **4. 与我们需求的匹配：**
> - 我们需要混合检索（稠密+稀疏）→ Milvus 原生支持
> - 我们需要按 product_id 过滤 → Milvus 支持标量过滤
> - 我们需要自建部署（数据是保险条款，有合规要求）→ Milvus 支持 Docker/K8s 部署
> - 我们用 LangChain → LangChain 有 Milvus 集成
> **对比其他选项：**
> - **FAISS**：Facebook 开源的向量检索库，性能好但只是个库，没有持久化、过滤、分布式能力，适合研究和小规模场景。
> - **Chroma**：轻量级，上手快，但功能简单，不支持稀疏向量和复杂过滤，适合原型。
> - **Pinecone**：全托管 SaaS，功能强，但闭源、成本高、数据在第三方，保险行业数据合规要求高，不适合。
> - **pgvector**：PostgreSQL 插件，能和业务数据共存，但向量检索性能不如专业向量库，不支持稀疏向量，数据量大了性能瓶颈明显。
> 综合来看，Milvus 在功能、性能、成本、数据可控性之间平衡最好，是我们项目的最优选择。

### Q5：什么是 Agentic RAG？和传统 RAG 有什么区别？为什么用 Agentic RAG？
**考察点：**RAG 架构演进理解、Agent 与 RAG 结合
**参考答案：**
> **传统 RAG（2-Step RAG）：**流程是固定的——用户提问 → 检索相关文档 → 把文档和问题一起交给大模型生成答案。不管什么问题，都强制走一次检索。
> **Agentic RAG：**把检索能力封装成一个 Tool（工具），交给 Agent（智能体），由 Agent 自主决定：
> - 这个问题需不需要检索？（闲聊不需要，事实性问题需要）
> - 用什么查询词检索？（可以根据上下文改写查询）
> - 检索一次够不够？（不够可以调整查询词再检索）
> - 检索结果怎么用？（可以结合多轮检索结果综合回答）
**核心区别：**

| 维度 | 传统 RAG | Agentic RAG |
| --- | --- | --- |
| 检索控制权 | 程序控制，每次都检索 | Agent 自主决定是否检索 |
| 查询词 | 直接用用户原问题 | Agent 可改写、优化查询词 |
| 检索次数 | 固定一次 | 可多次检索、迭代 |
| 闲聊场景 | 浪费检索，可能引入干扰 | 不检索，直接回答 |
| 复杂问题 | 单次检索可能不够 | 可多轮检索、多源整合 |
| 灵活性 | 固定流程，不灵活 | 灵活，可扩展更多工具 |
**我们为什么用 Agentic RAG：**
> 1. **保险顾问场景是多轮对话**，用户会闲聊、会问产品、会问条款，不是每个问题都需要检索条款。Agentic RAG 让 Agent 自己判断，闲聊不检索，节省开销，也避免无关上下文干扰答案。
> 2. **我们的 Agent 本身就有工具调用能力**（查产品、算保费、保存方案），把检索也封装成 Tool，架构统一，Agent 可以根据需要灵活组合工具。比如用户问"这款产品的等待期是多久，保费多少？"，Agent 可以同时调用检索 Tool 查条款、调用产品查询 Tool 查保费，然后综合回答。
> 3. **复杂问题支持多轮检索**。比如用户问"重疾险和医疗险有什么区别？"，Agent 可能先检索重疾险条款，发现不够，再检索医疗险条款，最后对比回答。传统 RAG 一次检索很难覆盖这种对比类问题。
> 4. **查询词优化**。用户的问题可能很口语化（"这个病赔不赔？"），Agent 可以结合上下文（之前在聊某款重疾险）生成更精准的查询词（"XX重疾险 疾病保障范围"），提升检索准确率。
> 当然，Agentic RAG 也有缺点：增加了系统复杂度，Agent 的判断可能出错（该检索的不检索），延迟可能更高（多轮调用）。但在我们的保险顾问场景下，灵活性和准确率的收益远大于成本。

## 4.2 Agent 与 LangGraph 相关高频题

### Q6：介绍一下你们的 Agent 架构，为什么用 LangGraph 而不是直接用 LangChain Agent？
**考察点：**Agent 架构理解、LangGraph 与 LangChain 的区别、技术选型
**参考答案：**
> 我们的 Agent 采用 **LangGraph 多 Agent 编排架构**，整体是一个主 Graph（Orchestrator）负责意图识别和路由，下面挂多个子 Agent / 子工作流。
> **主 Graph 结构：**
> - **route 节点**：意图识别，判断用户消息属于闲聊、保险推荐、理赔咨询、转人工还是无法识别，然后路由到对应节点。用大模型做意图分类，输出结构化的 RouteResult（intent + reason）。
> - **chitchat 节点**：闲聊子 Agent，处理日常对话，最终引导用户到保险咨询。
> - **recommendation_plan 节点**：保险推荐子 Agent，这是核心，支持工具调用（查候选产品、保存方案）和 RAG 条款问答。
> - **claim 节点**：理赔咨询子 Agent，查询保单、解释条款、说明理赔流程。
> - **human_handoff 节点**：转人工，记录请求后可接入人工客服系统。
> - **fallback 节点**：意图无法识别时，引导用户明确需求。
> **State 设计：**继承 LangChain 的 MessagesState，包含 messages（跨工作流共享的消息历史）、previous_workflow（上一轮工作流）、active_workflow（本轮工作流）。previous_workflow 用于上下文延续，比如用户上一轮在聊保险推荐，这一轮说"那它的保费呢"，路由时可以参考上一轮的工作流。
> **为什么用 LangGraph 而不是 LangChain Agent：**
> 1. **复杂流程控制**：LangChain 的 Agent（create_react_agent 等）是固定的"思考-行动-观察"循环，适合单 Agent 场景。但我们的场景是多工作流、多意图，需要明确的路由、条件分支、不同的子流程，LangGraph 的状态图（StateGraph）可以精确控制节点执行顺序和条件边，更适合复杂业务流程。
> 2. **持久化会话记忆**：LangGraph 原生支持 Checkpointer，可以把 Agent 的 State 持久化到 PostgreSQL，服务重启后通过 thread_id 恢复完整对话历史。LangChain Agent 的记忆管理相对弱，需要自己实现持久化。
> 3. **流式输出支持**：LangGraph 的 astream_events 可以细粒度地输出每个节点、每个工具调用的事件，我们基于它实现了 SSE 流式对话。
> 4. **可观测性和调试**：LangGraph 的状态图可以可视化，每个节点的输入输出都清晰，出问题容易定位。LangChain Agent 的执行过程相对黑盒。
> 5. **人机协作**：LangGraph 原生支持 interrupt（中断），可以在工具调用前暂停，等待人工确认后再继续，适合保险这种需要人工审核的场景。
> 简单说，LangChain Agent 适合"一个 Agent 循环调用工具"的简单场景，LangGraph 适合"多节点、多分支、多 Agent 协作"的复杂业务流程。我们的保险顾问有明确的意图路由和多个独立工作流，LangGraph 更合适。

### Q7：Agent 的工具调用是怎么实现的？如何保证工具调用的安全性？
**考察点：**Function Calling 原理、工具调用安全、工程实践
**参考答案：**
> **工具调用实现：**
> 我们基于 LangChain 的 Tool 机制和大模型的 Function Calling 能力实现工具调用。
> 1. **工具定义**：用 LangChain 的 @tool 装饰器定义工具，包含工具名称、描述、参数 schema（Pydantic 模型）。比如 query_candidate_products 工具，参数是 category（险种）、budget（预算）、limit（数量），描述要写清楚什么时候该调用这个工具。
> 2. **工具绑定**：把工具列表绑定到 ChatModel（bind_tools），大模型就知道有哪些工具可以调用。
> 3. **调用流程**：用户消息进入 Agent → 大模型判断是否需要调用工具 → 如果需要，输出 tool_call（工具名+参数）→ LangChain 执行对应工具，得到 ToolMessage → 把 ToolMessage 放回消息历史 → 大模型根据工具结果生成最终回答。这个过程可能循环多次（ReAct 模式）。
> 4. **方案推荐工作流的核心工具**：
> - query_candidate_products：按险种和预算查询候选保险产品
> - save_insurance_plan：保存 AI 生成的保险方案到数据库
> - 条款检索 Tool：RAG 检索，查询保险条款内容
> **工具调用安全：**
> 这是我们项目特别注意的一点，因为 save_insurance_plan 是写操作，不能让大模型随便调用，更不能让它伪造用户 ID。
> 1. **Context 机制传递用户身份**：我们用 LangChain 的 Context（RunnableConfig 的 configurable）传递当前用户 ID。user_id 不作为工具参数暴露给大模型，而是通过 ToolRuntime 注入。大模型看不到 user_id，也无法伪造。
> 2. **工具内部校验**：save_insurance_plan 工具内部从 runtime.context.user_id 获取当前用户，而不是从参数获取。确保方案归属正确，防止越权保存别人的方案。
> 3. **工具描述明确**：每个工具的描述要写清楚"什么时候该调用"、"参数含义"，减少大模型误调用。比如 save_insurance_plan 的描述明确写"只有在用户确认方案后才调用"。
> 4. **参数校验**：工具参数用 Pydantic 模型定义，有类型校验和约束（如预算必须大于0），非法参数直接报错，不会执行。
> 5. **写操作谨慎**：对于 save 这类写操作，可以考虑加人工确认环节（LangGraph 的 interrupt），或者在 Prompt 里明确要求"先展示方案给用户确认，再保存"。
> 6. **日志审计**：所有工具调用都记录日志（工具名、参数、结果、耗时），方便排查问题和安全审计。

### Q8：会话记忆是怎么实现的？为什么用 PostgreSQL Checkpointer？
**考察点：**Agent 记忆管理、Checkpointer 原理、工程选型
**参考答案：**
> **会话记忆实现：**
> 我们基于 LangGraph 的 **PostgreSQL Checkpointer（AsyncPostgresSaver）** 实现会话记忆持久化。
> 1. **原理**：LangGraph 每次执行（每次用户消息）都会产生一个 State 快照，Checkpointer 负责把这个快照持久化存储。下次调用时，通过 thread_id（会话ID）从 Checkpointer 恢复上一次的 State，包括完整的 messages 历史，这样 Agent 就有了上下文记忆。
> 2. **thread_id 管理**：我们的业务有 chat_threads 表，用户登录后可以创建多个会话。每个会话有一个 thread_id，调用 Agent 时把 thread_id 传入 config（configurable={"thread_id": xxx}），Checkpointer 就按这个 ID 存储和恢复状态。
> 3. **独立连接池**：Checkpointer 用的是 psycopg（异步 PostgreSQL 驱动）的连接池，和我们业务用的 SQLAlchemy（asyncpg 驱动）是隔离的，避免互相影响。
> 4. **会话删除**：用户删除会话时，不仅要删 chat_threads 表的记录，还要调用 Checkpointer 的 delete 方法，删除该 thread_id 下的所有 checkpoint，避免数据残留。
> 5. **消息历史查询**：前端需要展示历史消息时，我们从 Checkpointer 中获取最新的 State，提取 messages 返回。也可以用 get_state_history 获取所有历史快照。
> **为什么用 PostgreSQL Checkpointer：**
> LangGraph 支持多种 Checkpointer：MemorySaver（内存）、SqliteSaver（SQLite）、PostgresSaver（PostgreSQL）等。我们选 PostgreSQL 的原因：
> 1. **持久化**：MemorySaver 存在内存里，服务重启就丢了，生产环境不能用。PostgreSQL 是持久化存储，服务重启、扩容都不丢数据。
> 2. **我们已经用了 PostgreSQL**：业务数据都存在 PostgreSQL，Checkpointer 也用 PostgreSQL，不需要额外引入新的存储组件（如 Redis），运维成本低。
> 3. **支持异步**：AsyncPostgresSaver 是异步实现，和我们 FastAPI 异步架构匹配，不会阻塞事件循环。
> 4. **并发安全**：PostgreSQL 有事务和行锁，多实例并发写入同一个 thread_id 时不会冲突。
> 5. **数据可查询**：Checkpointer 的数据存在 PostgreSQL 表（checkpoints、blobs、writes）里，可以直接用 SQL 查询，方便调试和数据分析。
> **和其他方案对比：**
> - **Redis Checkpointer**：性能更好，适合高并发，但我们项目并发量不大，PostgreSQL 足够。而且 Redis 数据易失，需要配置持久化，多一层运维。
> - **自己实现记忆**：把 messages 存在业务表，每次调用时拼到 Prompt 里。这样做的问题是：只能存消息，不能存 Agent 的完整 State（如 active_workflow、工具调用中间状态）；需要自己管理消息截断、token 计数；LangGraph 的状态恢复、时间旅行（回退到之前的状态）等高级功能用不了。
> 综合来看，PostgreSQL Checkpointer 在功能、成本、运维之间平衡最好，适合我们的项目。

### Q9：SSE 流式对话是怎么实现的？为什么用 SSE 而不是 WebSocket？
**考察点：**流式输出实现、SSE vs WebSocket、异步编程
**参考答案：**
> **SSE 流式对话实现：**
> 我们基于 FastAPI 的 EventSourceResponse 和 LangGraph 的 astream_events 实现 SSE 流式对话。
> 1. **后端接口**：定义一个 POST /chat 接口，接收用户消息和 thread_id，返回 EventSourceResponse（FastAPI 对 SSE 的���装）。接口是异步生成器（async generator），不断 yield ServerSentEvent。
> 2. **Agent 流式调用**：调用 Agent 的 astream_events(version="v3") 方法，这是一个异步事件流，会产出各种事件（on_chat_model_stream、on_tool_start、on_tool_end 等）。
> 3. **事件过滤和提取**：我们只关注 on_chat_model_stream 事件（大模型生成文本增量），从事件数据中提取 message.text（AI 消息的文本增量），逐片段 yield 给前端。这样前端就能看到 AI 回复逐字输出。
> 4. **结束标识**：事件流结束后，发送一个 event: done 的 SSE 事件，告诉前端回复结束。
> 5. **异常处理**：用 try/except 包裹异步生成器，如果出错，发送 error 事件给前端，确保连接正常关闭。
> **为什么用 SSE 而不是 WebSocket：**
> 1. **场景匹配**：我们的场景是"服务端向客户端推送 AI 生成的文本流"，是单向的（服务端→客户端），客户端只需要在最开始发一次请求（用户消息）。SSE 天生就是服务端单向推送，完美匹配。WebSocket 是双向通信，对于我们的场景有点大材小用。
> 2. **实现简单**：SSE 基于 HTTP，FastAPI 原生支持 EventSourceResponse，不需要额外的依赖和配置。WebSocket 需要自己管理连接状态、心跳、重连、消息序列化，复杂度高很多。
> 3. **自动重连**：SSE 协议内置了断线重连机制，浏览器的 EventSource 对象会自动重连，还可以通过 Last-Event-ID 恢复断点。WebSocket 需要自己实现重连逻辑。
> 4. **兼容性好**：SSE 基于标准 HTTP，能穿过大多数防火墙和代理，不需要特殊配置。WebSocket 需要代理支持 Upgrade 头，有些企业网络会屏蔽。
> 5. **调试方便**：SSE 是纯文本，浏览器开发者工具直接能看到事件流，调试方便。WebSocket 是二进制或帧协议，调试需要专门工具。
> **SSE 的缺点和我们的应对：**
> - SSE 默认只支持 GET 请求，但我们需要传用户消息（POST body）。解决方案：用 POST 请求 + EventSourceResponse，FastAPI 支持。前端用 fetch + ReadableStream 读取 SSE，而不是原生 EventSource（原生只支持 GET）。
> - SSE 是单向的，客户端不能在连接中发新消息。但我们的场景是一次请求对应一次回复，用户发新消息会建立新的 SSE 连接，没问题。
> 总结：对于 AI 对话这种"服务端流式推送"场景，SSE 比 WebSocket 更简单、更合适。只有在需要双向实时通信（如多人协作、在线游戏）时，才选 WebSocket。

### Q10：大模型应用开发中，你遇到过哪些坑？怎么解决的？
**考察点：**工程实践经验、问题解决能力、对大模型应用的深度理解
**参考答案：**
> 大模型应用开发和传统后端开发很不一样，有很多独特的坑。我说几个我们项目实际遇到的：
> **1. 大模型输出不稳定，工具调用参数格式错误**
> 问题：大模型有时候不按 schema 输出工具参数，比如参数类型错误、缺字段、输出多余的解释文字，导致工具调用失败。
> 解决：
> - 用 LangChain 的 bind_tools，它会自动处理工具调用的解析和校验，格式错误会报错并重试。
> - 工具描述写得非常清楚，包括参数含义、取值范围、示例，减少大模型误解。
> - 用 Pydantic 定义参数 schema，有严格的类型校验。
> - 对关键工具调用加 fallback，如果失败了，让大模型重新生成一次。
> **2. 上下文窗口溢出，Token 超限**
> 问题：多轮对话后，messages 越来越长，加上检索到的条款内容，总 token 超过大模型的上下文窗口，导致报错。
> 解决：
> - 用 LangChain 的 trim_messages 对消息历史做截断，保留最近 N 轮，或者按 token 数限制。
> - 对系统 Prompt 和检索内容做精简，只保留最相关的信息。
> - RAG 检索的 TopK 不要太大，控制在 3-5 个父块。
> - 选择上下文窗口大的模型（如 DeepSeek 支持 128K），给足余量。
> **3. 大模型幻觉，编造不存在的条款内容**
> 问题：RAG 检索不到相关内容时，大模型可能自己编造条款信息，误导用户。保险条款是法律文件，幻觉后果严重。
> 解决：
> - Prompt 里明确要求："只能基于检索到的条款内容回答，如果检索内容中没有相关信息，直接说'根据现有条款无法回答'，不要编造。"
> - 要求答案附带来源（条款名称、章节），方便验证，也增加大模型编造的成本。
> - 对检索结果做相关性判断，如果 TopK 的相似度都很低，直接不检索，告诉用户没有找到相关条款。
> - 关键场景（如理赔条件、免责条款）可以加人工审核环节。
> **4. Agent 路由错误，用户意图识别不准**
> 问题：route 节点的意图识别有时候会错，比如用户问理赔相关问题，被路由到保险推荐。
> 解决：
> - 优化路由 Prompt，给每个意图写清楚定义和示例（few-shot）。
> - State 里记录 previous_workflow，路由时参考上一轮的工作流，比如上一轮在理赔，这一轮大概率还是理赔。
> - 对模糊意图，让大模型输出 reason（判断理由），方便调试和优化 Prompt。
> - 可以在路由后加一个确认环节，如果意图不确定，先问用户"你是想咨询保险方案还是理赔问题？"
> **5. 异步编程中的连接池和并发问题**
> 问题：FastAPI 异步架构下，数据库连接池、大模型并发调用、SSE 连接管理都有坑。比如 SQLAlchemy 异步 session 不能跨请求共享，Checkpointer 和业务用不同驱动导致连接池配置冲突。
> 解决：
> - 用 FastAPI 的依赖注入管理数据库 session，每个请求一个 session，请求结束自动关闭。
> - Checkpointer 用独立的 psycopg 连接池，和 SQLAlchemy 的 asyncpg 隔离，配置独立的连接数。
> - 大模型调用设置超时和重试，避免某个请求卡住占用连接。
> - SSE 连接设置心跳，防止代理超时断开。
> 这些坑都是大模型应用开发特有的，传统后端开发经验不一定能覆盖，需要在实践中不断踩坑和总结。
